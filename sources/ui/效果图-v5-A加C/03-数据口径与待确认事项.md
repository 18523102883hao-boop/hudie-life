# 数据口径与待确认事项

以下是源码阅读发现的实际差异，尚未改代码或核验服务端。效果图沿用历史示例，不自行改变业务含义。

## 1. 需要确认的核心问题

| 项目 | 已见源码行为 | 需要确认 / 建议处理 |
| --- | --- | --- |
| 折扣依据 | info.js 用 price / market_price × 10，保留一位；界面主价格却是 subsidy_price | 折扣描述的是标价还是自购到手价？先确认口径，再统一标签和公式，不能直接用画面价格反算替换 |
| 到手价来源 | normalizeSpecs 优先保留明确 subsidy_price；否则由 price 减去 max_commission，缺失再取 commission，按分处理 | 这些字段在服务端的业务定义和权限是否一致？缺失时沿用“价格待确认”等分支，不能用 0 假装免费 |
| 主销量和套餐销量 | 首屏用 sale_num；套餐 display_sale_num 用 sale_num + virtual_sale_num | 两处为什么不同？由业务/服务端确认真实可展示口径；效果图不凭空补销量 |
| 库存显示和售罄 | 显示 stock，但售罄判断为 stock <= today_sale_num | stock 是总额度还是实时剩余？today_sale_num 如何定义？确认后决定文案和计算，不擅自再减销量 |
| 参考价格 | 历史图有三人票门市价 1074，也有费用行 1611；无法由本地代码判断谁准确 | 商家核对套餐内容、单位价及参考价格来源；不能把两者混作同一原价 |
| 无效划线价 | 首屏模板直接展示 market_price；套餐区则以 >0 为条件 | 建议只展示已确认且有效的正数参考价；这是待实施建议，不是本次已修复 |
| 倒计时与状态 | 客户端 now_time 递增；不同判断处包含 > / < 的边界 | 核验等于结束时刻的状态、手机时间偏差、后台活动修改，以及提交订单时的服务端复核；本次未审计服务端 |
| 佣金与分享 | commission 为真才显示“自购省 / 分享赚”；海报由接口返回 | 展示资格、计算与结算规则需服务端证据；图中出现分享不等于已承诺可获佣金 |
| 套餐结构化内容 | enabled=1 且 groups 非空才展示费用包含 | 哪些商品已配置？未配置则保留富文本，不能从图片猜造结构化价格 |
| 地图与定位 | 无定位仍可显示门店；距离取数据；底图用原生 map | 检查定位、区域选择与距离计算来源；无距离就不显示，不能捏造“附近” |
| 权限入口 | 达人、视频号、门店、BD、导出等各自有条件 | 提供测试身份和权限矩阵后验证；未画出的分支不表示删除 |
| 服务端海报与素材 | 商品图片、二维码海报、配置多由接口提供 | 视觉确认后同时安排后台广告和海报模板更新，否则页面与分享图会不一致 |
